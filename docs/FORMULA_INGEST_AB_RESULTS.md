## 单独验证输出预算与清洗

固定修复后第一轮每题的**实际生成提示**，复核其哈希与后端记录一致。六道题各用 0.8B、temperature 0 和 top_p 1，分别直接请求 256 与 768 个输出 token，共 12 次额外生成。这一诊断不走 HTTP 引用修复，单独计数。六个较短原始输出全部是较长原始输出的完整前缀。

- **n06 找到了一个可以独立复现的输出清洗问题。** 768-token 配置下模型实际用了 402 个 token，原始正文正确写出 0.4 MHz 和最大偏差 200 kHz。应用清洗后，答复停在第二部分标题。离线重放同一原文，只放开 `unique_sentences[:12]` 的 12 段限制，200 kHz 就保留下来了。主实验的 256-token 样本在原始生成阶段就缺第二个结果，这与长答的清洗损失是两件不同的事。
- n02 延长后仍把十六进制数字串当十进制数值，n03 把 4.096/4096 V 算成 0.1 V，n04 混淆 4096 与 4095 的分母并把步长当成理想输出。n07 得到 1008 后又使用 mV 或 mΩ，n10 继续使用与题意无关的 DNL 公式。单独调高预算解决不了这些读式、运算与量纲错误。
